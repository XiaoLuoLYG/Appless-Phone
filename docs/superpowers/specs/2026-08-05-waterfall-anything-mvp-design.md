# Waterfall Anything 初版 Demo 设计

日期：2026-08-05

状态：设计已确认；仅形成规格，尚未实现

## 目标与非目标

Waterfall Anything 是 AIPhone 内独立的媒体发现体验。初版从现有 `media.aggregate.search` 进入；任一来源返回可展示候选即可在同一个 HTML 页面起流，不等待其他来源。页面切换为手机全屏、单条、纵向滑动的有限内容流，并为每条内容给出可核对的简短推荐理由。

目标：

- 用一个可复用的候选编排器，对统一候选做确定性去重、排序和来源均衡；
- 用媒体适配器复用现有视频、帖子和 HTML 渲染字段；
- 保留现有聚合搜索页作为入口，增加“进入发现流”；
- 让来源开关立即在本地重排，不重新请求 provider；
- 让后到候选只重排未展示队列尾部，并以内容水位线触发支持来源的小批续拉；
- 让餐饮、出行后续只需映射到同一最小候选字段即可复用编排器。

非目标：

- 不接管主 Agent、现有检索工具、业务页面、App 路由或导航；
- 不新增模型、依赖、数据库、行为持久化、异步 Agent 或自然语言输入，不伪造无限流；
- 不新增 provider 或改变授权逻辑；续流只复用来源已经提供的分页、游标或偏移能力，并保留 `sourceStatuses` 错误事实；
- 不实现餐饮、出行适配器，不建立接口、工厂或插件体系；
- 不重构现有聚合搜索页、A2UI 链路或 HTML 渲染框架。

## 真实现有代码事实

本规格以 2026-08-05 当前 working tree 为起点；其中已有用户未提交的聚合搜索修复，包含 X `messageText` 正文映射和隐藏 `result N` 占位标题。后续实现必须保留这些修复。

- `AggregateSearchClient.ets` 的 `callAggregateSearch()` 聚合 YouTube、B 站、X、Hacker News、Reddit 和知乎；当前实现按现有调用顺序等待并最终返回一次完整结果，尚没有“首个来源即起流”的渐进交付。
- `AggregateSearchTypes.ets` 将结果分为 `videos`、`posts`、`sourceStatuses`。视频已有来源、标题、摘要、原始链接、封面、发布时间和时长；帖子已有来源、标题、正文、原始链接、发布时间及扩展 `rows`。
- 当前去重只在视频列表和帖子列表内部按 URL（无 URL 时按 ID）分别执行，没有跨类型去重、相关性排序或来源打散。
- `AggregateSearchA2ui.ets` 把结果写入 `/aggregateSearch`；`HtmlHomeSnapshot.ets` 再映射为 `aggregate-video`、`aggregate-post` 和 `aggregate-source-status`。
- `HtmlAggregateSearchHomeRenderer.ets` 已生成独立 HTML 文档，按“视频 / 讨论”分区，已有类型与来源筛选、视频 iframe、帖子图片、元数据和原文链接；筛选完全在页面内 JavaScript 执行。
- `HtmlHomeRenderer.ets` 已按 `document.kind === 'aggregate-search'` 选择上述渲染器。因此发现流可在这份 HTML 内切换模式，无需新增页面路由。

## 三层架构

### 1. 候选编排器内核

一个无副作用的本地函数。输入为查询词、当前统一候选池、来源开关、已展示候选 ID、受保护的紧邻两条候选 ID，以及预留但初版不解析的 `preferenceDescription`；输出为排好序的未展示队列尾部和每条推荐理由。

它不读取网络、游标、存储或用户历史，也不认识媒体、餐饮、出行业务对象。初版来源开关是唯一可执行的轻量偏好规则；`preferenceDescription` 固定为空字符串，仅保留第二阶段输入位置。

### 2. 媒体适配器

媒体适配器复用现有来源调用，并把每个来源独立返回的小批结果映射为候选；它只负责来源级分页状态、同源单飞和字段转换，不参与排序。现有 `AggregateSearchVideo` 和 `AggregateSearchPost` 的映射如下：

| 候选字段 | 视频映射 | 帖子映射 |
| --- | --- | --- |
| `id` | 原 `id` | 原 `id` |
| `source` | 原 `source` | 原 `source` |
| `mediaType` | `video` | 有图片为 `image_text`，否则为 `post` |
| `title` | 原 `title` | 非占位的原 `title` |
| `summary` | 原 `summary` | 原 `text` |
| `url` | 原 `url` | 原 `url` |
| `coverUrl` | 原 `thumbnail` | `rows` 中 `mediaurl/image/images/thumbnail/cover/pic/picture` 的第一条有效 URL |
| `publishedAt` | 原 `publishedAt` | 原 `publishedAt` |
| `originalIndex` | 接收批次序号 + 批内原顺序 | 接收批次序号 + 批内原顺序 |

每个来源批次同时携带该来源的 `status`，以及经过 provider 能力确认的 `nextCursor/page/offset`；没有这些能力时明确标记本轮已结束，不猜测下一页参数。初版只增加这一种媒体映射，不为单个实现建立接口或工厂。未来餐饮、出行使用普通函数产出同一候选字段。

### 3. 沉浸式全屏发现流

扩展现有聚合搜索 HTML：入口态保留当前页面；点击“进入发现流”后，用同一文档内的容器显隐和样式状态进入全屏模式。内容区使用原生 CSS 纵向 `scroll-snap`，每屏一条，不引入手势库。

- `video`：复用现有封面、iframe 和原始链接；
- `image_text`：封面为主视觉，叠加标题与摘要；
- `post`：以正文、来源和时间为主，保留原文链接；
- 固定轻操作只有返回、来源偏好、推荐理由；内容自身继续使用现有播放或原文链接能力。

## 数据流

```text
现有 media.aggregate.search
  -> 各来源独立返回小批结果与来源状态
  -> 媒体适配器（分页状态、同源单飞、字段映射）
  -> 当前统一候选池
  -> 候选编排器（过滤、去重、尾部排序、理由）
  -> 当前 HTML 的稳定窗口 + 可重排队列尾部
```

同一 A2UI surface 可随来源批次更新 `/aggregateSearch`，不创建第二个工具或页面。`sourceStatuses` 继续在入口页和来源偏好层展示，不进入候选流。来源切换只把当前候选池和新开关重新传给编排器，不重新调用 provider。

## 随到随排与队列稳定

初始查询对启用来源分别发起已有的小批请求。第一批只要产生一条有效候选，入口即可显示“进入发现流”；其他来源保持 `loading`、失败、需授权或完成状态，均不阻塞起流。

队列分为三段：

```text
已展示 ID（永不回排）
  -> 当前条目之后的两条稳定窗口（被动到达不改）
  -> 可重排尾部（后到候选只进入这里）
```

- 后到候选先与已展示、稳定窗口和尾部做全局链接去重，再与原尾部一起确定性重排；
- 已展示内容不回到队列，稳定窗口固定为紧邻两条；不足两条时保护当前已有条目；
- 用户滑过一条后，稳定窗口前移一格，再从已排序尾部补足两条；
- 来源开关是用户显式操作，可以立即移除被关闭来源的未展示内容并重排全部剩余队列；当前条目若属于被关闭来源，则切到新队列第一条；
- 推荐理由随候选进入稳定窗口时固定，后到内容不会改写已展示或稳定窗口理由。

## 内容水位线续流

水位只计算“尚未展示且有效”的候选，包含稳定窗口和可重排尾部。初版使用固定 Demo 水位，不建立配置系统：

- 低水位：`3` 条；
- 补充目标：`8` 条；
- 单个来源每次最多请求 `5` 条。

首批请求同样限制为每个来源最多 `5` 条，不预取百条候选。

库存降到 `3` 条时，媒体适配器计算 `8 - 当前库存 - 在途预留数`，按来源轮转向仍有 `nextCursor/page/offset` 的来源请求所需小批。请求发出时先预留预计条数，避免多个来源同时把库存放大；去重或无效项导致实际不足时，再进行下一轮水位判断。

同一来源同一时间只允许一条续拉请求；其他来源可以并行。慢、失败或需授权来源只更新自身状态，不占用其他来源的续流机会，也不阻塞用户继续浏览。来源没有分页、游标或偏移时标记为本轮结束，不重复请求第一页。

## 候选池能力边界

排序只能在已有候选中选优，不能把低相关、重复或缺少有效内容的候选变好。初版候选池仅来自：

- 用户原查询下现有媒体来源返回的首批有限结果；
- 同一查询下、provider 明确支持的分页、游标或偏移小批续拉。

“广采、细排”是后续增强概念：先扩大并改善候选召回，再使用现有确定性编排器细排。初版 Demo 不主动换池、不改写查询、不从长期行为学习，也不增加自然语言通道。某来源本轮耗尽且没有续拉能力时如实标记结束；全部来源耗尽后显示“本轮内容已结束”，用户可用原查询手动刷新开始新一轮，不能循环旧内容或伪造无限流。

这里的上限是候选质量上限：水位线只能控制数量和时机，不能补救低质量召回。

## 规则排序细节

排序必须稳定且可复现，按以下顺序执行：

1. **来源过滤**：移除已关闭来源；空链接或非 HTTP(S) 链接不进入发现流，但仍保留在原聚合页。
2. **查询相关性**：查询、标题、摘要统一去首尾空白并做英文小写化；查询词只按空白和常见标点切分，无切分边界时只使用完整短语。完整查询短语命中或全部查询词命中为“强相关”，命中部分查询词为“相关”，否则为“弱相关”。同档内依次比较标题命中词数、摘要命中词数。
3. **新鲜度**：可解析时间按 `24 小时内 / 7 天内 / 30 天内 / 更早` 四档；缺失、无效或未来时间不获得新鲜度优势。
4. **链接级去重**：URL 去片段，协议和主机转小写，保留路径与查询参数；同一规范链接在可重排尾部只保留相关性更高、更新、原始顺序更靠前的一条，跨视频和帖子生效。若重复项已展示或进入稳定窗口，丢弃后到重复项，不替换稳定内容。
5. **来源均衡**：逐条选取时先比较相关性档，再优先出现次数更少的来源，然后比较新鲜度、命中词数和 `originalIndex`；来源计数以已展示内容和稳定窗口为起点。不开随机数，不改变来源内容。
6. **尾部输出**：保留已展示 ID 和紧邻两条稳定窗口，只输出其后的确定性队列；水位线续拉仍只增加同一查询的有限小批。

推荐理由只描述实际参与排序的机械信号，最多两项，例如“标题命中查询 · 24 小时内发布”或“相关内容 · 补充 Reddit 来源”。没有时间或命中证据时不得生成对应理由。

## 交互状态

| 状态 | 行为 |
| --- | --- |
| `entry` | 显示现有聚合搜索页；首个来源产生至少一条有效候选时即显示“进入发现流” |
| `discovering` | 全屏显示一条内容；纵向滑动切换，页面内记录当前候选 ID |
| `source_preferences` | 覆盖层切换来源；关闭后立即本地重排 |
| `reason_open` | 当前条目上展开确定性推荐理由，再次点击收起 |
| `replenishing` | 库存到低水位，后台小批续拉；当前内容和稳定窗口继续可用 |
| `exhausted` | 所有可用来源本轮结束，显示“本轮内容已结束”，可返回、调整来源或按原查询刷新 |

来源重排后，当前候选仍有效则保持当前位置；否则显示新顺序第一条。返回入口恢复进入发现流前的页面滚动位置和筛选状态。所有状态只存在当前 HTML 内存中，离开页面或获得新搜索结果即丢弃。

来源偏好默认开启所有已请求来源；面板显示各自的 `loading/success/empty/needs_auth/error/exhausted` 状态。只有拥有有效候选的来源参与本地重排。

## 错误与空态边界

- 所有 provider 都无候选：不显示入口按钮，沿用现有空态和 `sourceStatuses`。
- 首个 provider 有有效候选：立即允许起流，不等待其他 provider 完成。
- 部分 provider 慢、失败或需授权：成功来源仍可进入并续流；异常状态不伪装成内容卡。
- 用户关闭全部来源：停留在来源偏好空态并提示“至少开启一个来源”，不自动替用户开启。
- 候选缺封面：使用现有纯色/文字布局，不生成假图；缺摘要时只显示标题；缺时间时不展示新鲜理由。
- 视频嵌入失败：保留原始链接供用户打开，不宣称播放成功。
- 原始链接无效：该条不进入发现流，原聚合页和 provider 状态不受影响。
- 续拉返回重复或无效候选：不进入队列，重新计算水位；不循环展示旧内容。
- 来源不支持分页、游标或偏移：本轮只消费已有有限候选，结束后允许按原查询刷新。
- 所有可续拉来源耗尽：进入 `exhausted`，不改写查询、不换池、不伪造下一页。

## 最小验证方案

1. 在现有聚合搜索单测附近增加一个纯函数检查，覆盖稳定排序、强/弱相关、新鲜度、跨类型 URL 去重、来源均衡、来源关闭和理由事实。
2. 增加一个渐进批次检查：首个来源到达即可产出；后到高相关候选只重排尾部；已展示和紧邻两条、对应理由保持不变。
3. 覆盖水位 `3 -> 8`、单批最多 `5`、同源单飞、在途预留、重复批次、无游标结束，以及慢/失败/需授权来源不阻塞。
4. 在现有 HTML renderer 测试中覆盖视频、图文、帖子映射，确认占位标题不回归，并验证入口、同页模式切换、三项轻操作、本地来源重排、续流中和本轮结束状态。
5. 验证空候选、全部来源关闭、缺封面/时间、部分 provider 失败和嵌入失败边界；不为该功能引入新测试框架。
6. 用真实 `media.aggregate.search` 查询在 HarmonyOS 真机验收：首个可用来源即起流、迟到来源不改变稳定窗口、低水位小批续拉、无分页来源诚实结束、原始链接可打开、provider 错误如实保留。构建成功不能替代 Hypium 断言结果和真机可见证据。

## 第二阶段边界

技术概念统一称为“对话式推荐共创”，用户体验名称为“随聊随变”，不称“自然语言纠偏”。

第二阶段可以把独立发现流内的对话输入转换为临时、结构化偏好，再交给同一个候选编排器重排；初版仅预留 `preferenceDescription`，不展示输入框、不解析自然语言、不调用主 Agent、不持久化描述。模型、异步 Agent、长期行为画像、数据库，以及对餐饮/出行的真实适配，都必须在初版真机验证后另行设计和批准。

## 初版实现范围原则

三层是职责边界，不是三个框架。实现时优先在现有聚合来源调用、结果映射与 `HtmlAggregateSearchHomeRenderer.ets` 中复用字段、HTML、筛选和链接安全逻辑；只增加一条最小渐进批次/续流通道、一个纯编排函数及对应检查，不进行未请求重构。
